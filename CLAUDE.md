# CLAUDE.md

draw-ex: a Tauri v2 desktop app (Windows + macOS) that shows live camera footage of a
real _Yu-Gi-Oh!_ duel with side panels of the cards the DRAW 2 models recognize.
`README.md` is the design source of truth: architecture, pipeline, cache, roadmap. Read it
before any design-level change, and update it in the same change whenever a decision
moves.

Status: contracts (F2b) in place: every crate's public API, the IPC commands and events,
and the generated TypeScript bindings, all backed by stubs. Crate bodies are `todo!()`
and IPC handlers return canned data. No real recognition, tracking or card data yet.

Implementing a ticket: read its entry in `docs/ROADMAP.md` first, and change only the
paths listed under its **Owns**. Its **Done when** list is the merge bar.

## Commands

Prerequisites: rustup (the toolchain is pinned in `rust-toolchain.toml` and installs
itself), Node.js LTS, pnpm (version pinned in `package.json` `packageManager`), and the
Tauri v2 OS prerequisites. Run everything from the repo root.

- Install: `pnpm install`
- Run the app: `pnpm tauri dev`. The dev server port defaults to 1420; set
  `DRAW_EX_DEV_PORT` to use another one (`DRAW_EX_DEV_PORT=1425 pnpm tauri dev`). Vite
  reads it in `vite.config.ts`, and `scripts/tauri.js` passes the matching `devUrl` to
  `tauri dev` via `--config`. Both use `scripts/dev-port.js`.
- Frontend only (browser, no Tauri): `pnpm dev`
- Checks (CI runs all of them, on macOS and Windows):
  - `cargo fmt --all --check`
  - `cargo clippy --workspace --all-targets -- -D warnings`
  - `cargo test --workspace`, then `git diff --exit-code src/lib/bindings.ts` (fails
    if the committed bindings are stale)
  - `pnpm check` (svelte-check + `tsc` for the Node-side config files)
  - `pnpm lint` (ESLint)
  - `pnpm format:check` (Prettier; `pnpm format` fixes. Markdown is excluded)
  - `pnpm test` (Vitest)
- Regenerate the TypeScript bindings: `cargo test -p draw-ex` (any `cargo test` that
  includes `src-tauri`). It rewrites `src/lib/bindings.ts`; commit the result.
- Build: `pnpm build` (frontend into `dist/`), then `cargo build --workspace`.
  Installers are not set up yet (ticket R1).

TypeScript is pinned to `~6.0` because `typescript-eslint` and `svelte-check` do not
support TypeScript 7 yet. Lift the pin when their peer ranges do.

## Layout

Domain terms are defined in `GLOSSARY.md`; boundary decisions are in `docs/adr/`.

- `crates/domain/`: shared IDs and geometry (passcode, camera, player, point, quad). No
  dependencies on the other crates.
- `crates/tracker/`: tracks, voting, confirmation, player assignment. No Tauri
  dependency. It takes its own `Observation` input and **never depends on draw-core**
  (ADR-0002).
- `crates/card-db/`: YGOPRODeck client, SQLite store, image cache, deck lists. No Tauri
  dependency.
- `src-tauri/`: the app shell. Keep commands thin and put the logic in the crates. It is
  the only crate that depends on draw-core.
- `src/`: Svelte 5 + TypeScript frontend. The IPC types come from `tauri-specta`:
  regenerate them after changing a command or event, rather than editing the generated
  file.

## Contracts

F2b fixed every interface Phase 1 builds against. Phase 1 tickets change only the inside
of the modules they own (pre-created, each with an "Owned by" comment). They do not
change the contract.

- **IPC**: `src-tauri/src/ipc/`. `commands.rs` and `events.rs` hold the typed commands
  and events, `types.rs` the payload types, and `frames.rs` the raw `submit_frame`.
  `convert.rs` is the only place where draw-core types are mapped to IPC types.
  `lib.rs` registers everything once. Commands reject with `IpcError { kind, message }`.
- **Bindings**: `src/lib/bindings.ts` is generated by tauri-specta, so never edit it.
  Regenerate it with `cargo test -p draw-ex` and commit it; CI fails when it is stale.
  ESLint and Prettier skip it.
- **`submit_frame`** (ADR-0003) is the one untyped command. Its body is raw RGBA8 bytes,
  and its headers are `draw-ex-camera-id`, `draw-ex-frame-width`,
  `draw-ex-frame-height` (pixels, `u32`) and `draw-ex-frame-time-ms` (finite `f64`).
  The frontend calls it through `src/lib/frames.ts`, which must stay in sync with
  `frames.rs`.
- **Card image URLs**: `cardimg://<size>/<passcode>` (`full | small | cropped`), built
  by `src/lib/card-image.ts`. I1 registers the protocol.
- **Units**: coordinates are `f32` source-frame pixels; passcodes are integers; scores
  and confidences are 0 to 1; times named `*_ms` are milliseconds from the frontend's
  `performance.now()`. The one exception is `SessionInfo.startedAtMs`, which is
  wall-clock milliseconds since the Unix epoch. Payloads use camelCase keys and enum
  variant names. Tagged enums carry a `kind` field.
- **Numbers in TypeScript**: `u64` values (byte counts, track IDs) are exported as
  `number`. They are exact below 2^53, which no byte count or ID here reaches. Float
  fields use `#[specta(type = domain::FiniteNumber)]` so that they export as `number`
  rather than `number | null`.
- Changing the contract itself takes a small PR to `main` that the other branches
  rebase onto (see the conflict hotspots in `docs/ROADMAP.md`).

## Recognition lives in the draw2 fork, not here

Card recognition is the `draw-core` crate in the draw2 fork
(https://github.com/VillegasMich/draw2, `crates/draw-core/`; local checkout at `../draw2`).
draw-ex consumes it as a pinned Cargo git dependency.

- **Recognition changes go in draw2.** That covers preprocessing, ONNX sessions,
  orientation, classification, deck filtering and the model manifest. Make the change
  there, tag a release, and bump the pin here. draw-ex code only calls draw-core's public
  API.
- **Stateless frame → cards is draw-core; anything across frames or duel-specific is
  draw-ex** (`tracker`). If a fix seems to need draw-core internals, the fix belongs in
  draw2.
- **Model files come from draw-core's manifest.** draw-ex downloads exactly what the
  manifest lists. Keep model names, revisions and hashes out of this repo.
- **Local co-development** uses the gitignored `.cargo/config.toml` `[patch]` override
  described in the README. Before committing a dependency bump, confirm the build passes
  with the override removed.

## Invariants

- **Display never waits for inference.** The `<video>` element shows the camera at its
  native rate. Inference takes at most one frame per camera in flight, and new frames
  are skipped while it is busy.
- **Only confirmed tracks reach the UI panels and the duel log.** Raw per-frame
  detections are used only for drawing boxes on the overlay.
- **Passcode is the card identity everywhere.** Normalize it to an integer, because
  sources pad it with leading zeros.

## YGOPRODeck usage (IP-ban risk)

The API blocks an IP for 1 hour above 20 requests/second, and blacklists clients that
hotlink images or keep re-fetching data (https://ygoprodeck.com/api-guide/). draw2 once
needed an emergency fix for exactly this. So:

- Send every YGOPRODeck request through `card-db`'s single shared rate limiter.
- Fetch each image once, store it on disk, and serve it to the webview from the local
  cache. Frontend code references local image URLs only.
- Bulk-sync `cardinfo.php` into SQLite, and re-sync only when `checkDBVer.php` reports a
  new `database_version`.
- Tests and dev loops use recorded fixtures, never the live API.

## Platform notes

- macOS camera access in the webview needs `NSCameraUsageDescription` in `Info.plist`
  plus the `com.apple.security.device.camera` entitlement for hardened-runtime and
  notarized builds. Both are in place:
  - `src-tauri/Info.plist` holds `NSCameraUsageDescription`. The bundler merges it into
    the app's `Info.plist`, and for `tauri dev` tauri-codegen embeds it into the debug
    binary, so dev builds need nothing else.
  - `src-tauri/entitlements.plist` holds the camera entitlement. `tauri.conf.json`
    references it from `bundle.macOS.entitlements`; bundles use the hardened runtime by
    default.
  - The WKWebView never asks on its own: with no `on_permission_request` handler, wry
    grants the page's media-capture request. The only prompt is macOS's camera prompt.
    Under `tauri dev` the unbundled binary's prompt and permission belong to the app that
    launched it (the terminal or IDE), so allow the camera there in System Settings →
    Privacy & Security → Camera. If that app already has camera access, no prompt
    appears at all (seen when D1 was verified).
- Windows camera access goes through WebView2. With no permission handler, WebView2
  shows its own browser-style prompt on the first `getUserMedia` and saves the answer in
  the webview profile, per origin (dev `http://localhost:<port>` and the bundled app are
  different origins). Windows Settings → Privacy & security → Camera → "Let desktop apps
  access your camera" must be on. To skip the prompt, `src-tauri` could grant
  `PermissionKind::Camera` in an `on_permission_request` handler (not done).
- ONNX Runtime (via draw-core's `ort` dependency): CoreML on macOS, DirectML on Windows,
  CPU fallback. The runtime library must end up inside the Tauri bundle. Verify a
  packaged build on a clean machine, not only `tauri dev`.
